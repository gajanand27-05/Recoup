# EXPERIMENT.md — pre-registration

**Committed and pushed before any batch run. That ordering is the point of this file.**

What makes it evidence is not the date written below — a date in a file is written by whoever
writes the file. It is the **pushed commit** and **GitHub's own record of when it arrived**,
verifiable by anyone:

```bash
git log --diff-filter=A --format='%H %ai' -- EXPERIMENT.md    # when this file was added
git log --format='%H %ai' -- runs/                            # when any run artifact appeared
```

Same reasoning as the simulator freeze tag: the label is convenient, the pushed history is the
evidence. `tests/test_prereg.py` fails the build if any run artifact contains ledger rows
timestamped before this file's commit.

---

## Hypothesis

An LLM-driven recovery agent, constrained by an external policy engine, recovers a greater
share of halted subscriptions than fixed-interval outreach, over a 30-day window.

## Design

Randomised, two arms, balanced allocation.

- **Control** — fixed-interval outreach. Payment link reissued on a fixed schedule with fixed
  template copy. No decisioning. This is what a competent merchant does by hand once a
  subscription halts.
- **Treatment** — agent-decided outreach: channel, timing, copy, escalation, stopping.

Assignment: `sha256(customer_id + EXPERIMENT_SALT)`, low bit. Deterministic, so replay
reproduces allocation exactly.

## Sample size

**N = 2,000 (1,000 per arm)**, from a two-proportion power calculation at alpha = 0.05,
power = 0.80, baseline p1 = 0.51.

The baseline is **sourced, not assumed**: Stripe Smart Retries alone, Churnkey 5.4M failures.
It is read at runtime from the frozen simulator registry (`PARAMS.lock.json`), not typed, so
the number in this calculation is provably the one that was frozen.

The table below is **generated by `python -m recoup.eval.power`**, not transcribed. A test
extracts the block and compares it against a fresh render, because a hand-typed table goes
stale silently the moment `p1` changes — which would defeat the reason `p1` is read from the
registry at all.

**This design cannot detect an effect smaller than 6.23 percentage points.** A null result

## Primary metric

Recovery rate — share of halted subscriptions reaching `recovered` within 30 simulated days.
Interval: Newcombe-Wilson for the difference of proportions.

## Secondary metrics

- Rupees recovered per arm. Interval: percentile bootstrap, 10,000 iterations.
- Cost per rupee recovered, reported **twice**: marginal, and fully loaded with one-time DLT
  registration amortised over N.
- Messages sent per recovery.
- Policy veto rate, broken down by rule class.
- False-positive cost: spend on subscriptions where `would_self_recover` is true.
  **Computed in a separate module that never touches lift.**

## Analysis plan

Two-proportion z-test on the primary metric. Significance at alpha = 0.05, two-sided. Lift is
computed **from the control arm only**. Ground-truth labels are never used in the lift
calculation — enforced by module boundaries and by
`tests/test_firewall.py::test_lift_never_touches_ground_truth`.

Every reported figure is accompanied by its transport split. `real` and `sim` rows are never
pooled, and `eval.transport_split.require_declared_split()` raises rather than silently
rendering a single number when the split is mixed or empty.

## Stopping rule

The run ends at N = 2,000. **No optional stopping. No peeking and extending.**
If the result is null, the result is null and it gets reported as null.

## A/A test — declared in advance, in full

Before the main run, both arms execute the identical policy. If the harness reports lift where
none was injected, it manufactures lift and every number this project produces is void.

**This is the one measurement in the project where a NULL result is the success condition**,
which inverts every incentive elsewhere in the build. The parameters are therefore fixed here,
in advance, in the file whose commit timestamp is the evidence:

| | |
|---|---|
| **Seed** | **20260831** — the date this pre-registration was written. Chosen for being externally checkable rather than selected |
| **N per arm** | **1,000** |
| **Batch** | separate `run_id`, drawn from **outside** the powered 2,000 (D-032), so the pre-registered N is not silently reduced |
| **Expected result** | **no significant difference, p > 0.05** |

### What happens if the A/A shows a difference

**It is not re-run with a new seed.** Re-running until a clean result appears is optional
stopping wearing a different hat, and it would destroy the evidential value of every other
number here.

If the A/A fails:

1. It is recorded in `INCIDENTS.md` **with the failing seed and the observed p-value**, at the
   moment it happens.
2. It is treated as **a finding about the harness**, and the harness is investigated. Candidate
   causes, in order of likelihood: a broken assignment hash (not balanced, or correlated with
   an outcome-relevant field); a seed collision between the A/A batch and the main batch; the
   identifier-collision class already caught once in Task 9, where positional-only IDs made two
   batches share subscription IDs.
3. The fix is to the harness, and the A/A is re-run **only after a fix**, with the same seed,
   and both runs are reported.
4. If no cause is found, that is reported as an unresolved finding and the main result is
   presented as unreliable.

### What this A/A does and does not establish

**It validates the statistical machinery, not the pipeline.** `run_aa` draws two Bernoulli
samples at the same rate and pushes them through the same interval and test code the report
uses. It therefore cannot detect a broken assignment hash, a seed collision, or an identifier
collision — because it never touches assignment, the ledger, or replay.

Those failure modes are exactly what an A/A is supposed to catch, so a **second, pipeline A/A**
is pre-registered here:

> **After Task 22 and before the main batch**, a full-pipeline A/A runs both arms on the
> identical control policy through the real path — generator → arm assignment → transport →
> ledger → replay → lift — on its own `run_id` outside the powered N. Expected result: no
> significant difference. The same no-reruns rule applies.

Reporting the statistical A/A as though it validated the harness would be a claim the test
does not support. It is named this way now so the distinction cannot be blurred later.

**The A/A's own power is the same as the main design: 6.23pp at 1,000 per arm.** So a passing
A/A rules out harness bias **larger than about 6 percentage points**. It does not establish
that the harness is unbiased. Stated because a passing A/A is otherwise easy to over-read, and
this file exists to stop exactly that.

## What would falsify this

Each has a defined observable, a defined date, and a task that runs it.

- **A/A reports significant lift** → the harness manufactures lift. *(Task 13, statistical;
  Task 22, pipeline)*
- **Sensitivity sweep flips the sign** → the effect is an artifact of an assumed parameter.
  *(Task 23b — swept over every parameter marked `ASSUMPTION` in `simulator/PARAMS.md`, at both
  endpoints of its declared range. `self_recovery_rate_soft` and `_hard` are swept first,
  because they define the counterfactual and dominate. The **sign** is reported, not only the
  magnitude: any corner of any range where the treatment arm loses is reported, not excluded.)*
- **A parameter cannot be shown to move the model** → it is reported as **unwired**, never as
  **insensitive**. A swept parameter nothing reads produces a flat line, and a flat line reads
  as robustness. *(A-017, INC-005)*
- **`verify-ledger` fails** → the audit trail is decoration. *(Task 4, continuous)*
- **Adversarial eval shows an injection reaching an executed money action** → the
  bounded-agent thesis is false regardless of the architecture diagram. *(Task 21, Day 4)*

**Every item on this list is committed to running.** A pre-registration naming a falsification
test that is then skipped is the precise failure this file exists to prevent — and it is
findable by diffing two files in this repository.

## Known limitations of this design

Stated here rather than left to be found. The full list is in [`README.md`](README.md).

- **The counterfactual is assumed, not measured.** `would_self_recover` is generated from two
  unsourced parameters. Nothing published gives a post-halt, no-outreach recovery rate.
- **10 of 17 frozen simulator parameters are `ASSUMPTION`.**
- **The outcome oracle is a simulator** for the measured batch. Real transport is exercised
  separately and never pooled with it.
